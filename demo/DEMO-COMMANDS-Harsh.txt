1. REPLICATION (dashboard tab #rep, about 2 minutes)
================================================================================
Every write goes to the primary and is streamed to all three laptops.
One replica (sync) must confirm before a commit is acknowledged.

Step 1 [TERMINAL] replication topology on Branch A's primary:
$ pgA "select application_name, client_addr, state, sync_state, replay_lag from pg_stat_replication"
Expected:
 application_name | client_addr |   state   | sync_state
 pg-a2            | 10.60.13.12 | streaming | async
 pg-a3            | 10.60.1.152 | streaming | sync
Say: The primary streams its write-ahead log to both replicas. pg-a3 is
synchronous: no commit is acknowledged until it has the data.

A transfer from Branch A to Branch B changes two separate databases. The
coordinator runs 2PC so both halves commit, or neither does.

Step 1 [TERMINAL] cross-branch transfer with every 2PC step:
$ ~/Desktop/ADBMS/distbank/demo/transfer.sh A-1001 B-1001 500
Expected:

 txn_id : 9e28d72a2b83          <- copy this id for steps 2 and 3
 kind   : 2pc
 state  : COMMITTED
 steps  :
        230 ms  coordinator log: STARTED
        467 ms  phase 1: PREPARE TRANSACTION ok on branch A (A-1001 -500)
        602 ms  phase 1: PREPARE TRANSACTION ok on branch B (B-1001 +500)
        750 ms  coordinator log: decision = COMMIT (durable)

commit point. Phase 2 commits both.

6. RECOVERY (dashboard tab #rc, about 3 minutes)
================================================================================
If the coordinator crashes in the middle of a 2PC transfer, the next leader
finishes it from the durable log. A crashed database node rejoins as a replica.
FIRST: stop customer traffic (tab #av) and make sure ./cluster.sh leader shows
at least 2 coordinators alive (restart a killed one with "docker start
coordinator" on its laptop).

--- A. Coordinator crashes in the middle of a transfer ---

Step 1 [DASHBOARD] tab #rc -> choose "After logging COMMIT" -> click "Send & crash coordinator"
(Terminal alternative - crashes the leader on purpose:)
$ curl -s -m 5 -X POST http://$(leader):8000/transfer -H 'content-type: application/json' -d '{"from_account":"A-1001","to_account":"B-1001","amount":500,"fault":"crash_after_decision"}'

Step 2 [TERMINAL] immediately (within 15 s): the transfer is stuck in doubt on BOTH branches:
$ pgA "select gid, prepared from pg_prepared_xacts"; pgB "select gid, prepared from pg_prepared_xacts"
$ pgA "select txn_id, state from txn_log order by created_at desc limit 1" coordlog
Expected:
 [Branch A primary ...]  bank-5bf47433d643 | 2026-11-25 ...
 [Branch B primary ...]  bank-5bf47433d643 | 2026-11-25 ...
 5bf47433d643 | COMMITTING
Say: Both branches promised to commit and hold their row locks. They may not
decide alone - this is the blocking problem of 2PC.

Step 3 [TERMINAL] after 15-20 s: a new leader has finished the transfer from the log:
$ ./cluster.sh leader
$ pgA "select gid from pg_prepared_xacts"; pgB "select gid from pg_prepared_xacts"
$ pgA "select txn_id, state, note from txn_log order by updated_at desc limit 1" coordlog
Expected:
 Leader: {"name": "Yash", ...}
 (0 rows)   (0 rows)
 5bf47433d643 | COMMITTED | resolved by recovery: COMMIT PREPARED on A, B

Step 4 [NEW LEADER'S LAPTOP] show recovery in its log:
$ docker logs --tail 20 coordinator | grep -E 'election|recovery'
Expected:
 [election] Yash is the new leader: running crash recovery from the log
 [recovery] txn 5bf47433d643: log says COMMITTING -> COMMIT PREPARED on A, B -> COMMITTED
Say: The new coordinator never saw this transfer. It finished it only by
reading the durable log.

Step 5 [CRASHED LAPTOP] bring the crashed coordinator back (rejoins as standby):
$ docker start coordinator
(If Harsh was the leader that crashed, run it on THIS laptop.)

Step 6 [DASHBOARD] repeat with "Before deciding", then check after 15-20 s:
(Terminal alternative:)
$ curl -s -m 5 -X POST http://$(leader):8000/transfer -H 'content-type: application/json' -d '{"from_account":"A-1001","to_account":"B-1001","amount":500,"fault":"crash_before_decision"}'
$ pgA "select txn_id, state, note from txn_log order by updated_at desc limit 1" coordlog
Expected:
 2388d4af5f55 | ABORTED | resolved by recovery: ROLLBACK PREPARED on A, B
Say: No decision was logged, so the safe choice is to roll back on both
branches - presumed abort.
(Then run "docker start coordinator" again on the laptop that crashed.)

Step 7 [TERMINAL] all transfers ever finished by recovery:
$ pgA "select txn_id, state, note, updated_at from txn_log where note like 'resolved by recovery%' order by updated_at desc limit 10" coordlog
Expected:
 2388d4af5f55 | ABORTED   | resolved by recovery: ROLLBACK PREPARED on A, B | ...
 5bf47433d643 | COMMITTED | resolved by recovery: COMMIT PREPARED on A, B   | ...

================================================================================

  -> run: source ~/Desktop/ADBMS/distbank/demo/helpers.zsh   (in that terminal window)

no local database container (pg-a2 / pg-b2) is running
  -> start them: cd ~/Desktop/ADBMS/distbank/multi && ./cluster.sh node up pg-a2 pg-b2

zsh: command not found: select ...
  -> the command was split over several lines when pasting. Paste it as ONE line.

leader prints NONE
  -> a coordinator election is in progress; wait 15 s. If it persists,
     run "docker start coordinator" on each laptop.

pgA prints nothing / connection error
  -> Branch A is mid-failover; wait 30-40 s and retry.
     Check: docker exec pg-a2 patronictl list

./cluster.sh status shows a node stopped
  -> on its laptop: ./cluster.sh start <node>

Nodes stay "replica" after everyone starts, log says "not the healthiest node"
  -> the laptop whose nodes were primary at shutdown is not on yet; it holds
     the newest data. Start that laptop; the others then follow by themselves.

Nodes exit right after starting ("No more machines in the cluster")
  -> etcd has no majority: at least 2 laptops must be on the same Wi-Fi.
     Check: docker exec etcd-member etcdctl endpoint health --cluster

Docker is not running ("Cannot connect to the Docker daemon")
  -> open -a Docker, wait ~30 s, then: ./cluster.sh node up pg-a2 pg-b2 && ./cluster.sh candidate up

A laptop's IP changed
  -> update cluster.env identically on every laptop, or reconnect to the
     original network.
